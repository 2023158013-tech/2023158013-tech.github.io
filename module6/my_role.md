# ⚙️ 맡은 기능 (모듈 6)

정산·재무·체크리스트·이미지 네 도메인에 걸쳐 약 40개의 API를 빠르게, 그리고 빠짐없이 구현해 팀 전체 개발 속도를 받쳤습니다. 기능 구현과 별개로 DBA 역할로서 ERD 최신화, Flyway 도입을 위한 자료 조사와 공유, 초기 스키마 마이그레이션 순서 정리, 그리고 프로젝트 템플릿처럼 자유도가 필요한 데이터를 어떤 저장소로 다룰지에 대한 검토(MongoDB vs MySQL+MyBatis)까지 맡았습니다. (기능별 문제 해결·트러블슈팅은 별도 회고 문서에서 다룹니다 — 이 문서는 "무엇을 맡았는지"에 집중합니다.)

## 👥 팀 구성 및 협업 환경

* **팀 구성**: 백엔드 6명(JSON 응답) / 프론트 2명
* **담당 역할**: 정산·재무 도메인(CSV 업로드, 중복 검증, 매칭·동시성) / 체크리스트 도메인 / 이미지 도메인(S3 연동, 동시성, 성능) / 텍스트 도메인 전반 + DBA(ERD·Flyway·스키마 설계
* **협업 도구**: GitHub(PR·이슈), Notion(`.ai/` 문서 체계 — API 명세·컨벤션·인프라 문서), CodeRabbit(PR 자동 리뷰), Claude Code(IntelliJ 연동 AI 페어 프로그래밍)
* **핵심 타깃**: 도메인 4개를 혼자 커버할 수 있는 개발 속도와 꼼꼼함으로 프로젝트 기획의 안정성을 확보하여 기여 / DBA로서 스키마·마이그레이션 방향에 대한 팀 차원의 의사결정 기여

## 💡 핵심 구현 및 예외 방어 혁신

* **은행별 CSV 양식 추상화**: 금액(구분+금액 / 입금액+출금액)과 일시(통합 / 분리) 2축의 조합으로 4가지 표기 유형을 하나의 파이프라인으로 흡수. 세금계산서는 매입/매출 자동 구분 로직 신규 구축.
* **중복 검증 4단계 확장**: 실제 자동이체 오판 사례를 계기로 검증 기준을 `일시·금액·은행명` → `+잔액` → `+타입, 잔액 NULL 치환` → `+잔액 존재 여부`까지 4차에 걸쳐 확장, 최종 7개 컬럼 조합으로 정합성 확보.
* **상황별로 다르게 설계한 동시성 제어**: 입출금은 매칭 시 정산 블록 상태가 반드시 바뀌는 걸 이용한 조건부 UPDATE, 세금계산서는 상태가 안 바뀌는 경우가 있어 `FOR UPDATE` 행 잠금 — 같은 재무 영역이어도 경합 지점의 성격에 따라 구현을 달리 선택.
* **실측 기반 성능 최적화**: `EXPLAIN` 결과를 근거로 복합 인덱스·CTE·배치 처리를 도입해 filesort·풀스캔·N+1을 제거.
* **프론트 요청 기반 API 스펙 리팩토링**: 입출금/세금계산서 단건 조회 API 신설, 응답에 `bankName` 추가, 이미지 단건 삭제 시 `orderIndex` 재정렬과 `version` 동시 반영, 정산 현황 계좌번호 마스킹 해제(재무 권한자 한정) 등 실제 사용 흐름에 맞춘 정밀 조정.

### 이미지 (10개)

**항목 조회(다음/이전)**
* 무엇: 한 블록에서 다음/이전 버튼으로 이미지 하나씩 조회한다. 마지막에서 다음을 누르면 첫 이미지로, 첫 이미지에서 이전을 누르면 마지막으로 순환 조회되도록 백엔드에서 처리.
* 예외: `direction` 값 이상 → "direction 값이 올바르지 않습니다." / 접근 권한 없음 → "접근 권한이 없습니다."(조회 권한자도 볼 수 있어야 함) / 활성 이미지 없음 → "존재하지 않는 항목입니다." / 블록 없음 → "존재하지 않는 블록입니다."

**항목 전체 조회**
* 무엇: 한 블록의 이미지 전체 정보를 응답한다. 페이지/다음·이전 조회가 전체 배열을 한 번도 안 내려줘서, 수정 시 전체 배열이 필요해 신설.
* 예외: 권한 없음 → "편집 권한이 없습니다."(조회지만 수정용 API라 편집 권한으로 검증) / 블록 없음 → "존재하지 않는 블록입니다."

**다운로드**
* 무엇: 블록 안 이미지를 다운로드. 하나만 받으면 원본 파일명 그대로, 전체 받으면 블록명 zip으로(동명 파일은 번호 부여).
* 예외: 접근 권한 없음 → "접근 권한이 없습니다."(viewer 권한이면 가능) / 항목 없음(단건) → "존재하지 않는 항목입니다." / 이미지 없음(전체) → "다운로드할 이미지가 없습니다." / 블록 없음 → "존재하지 않는 블록입니다."

**휴지통 조회**
* 무엇: 소프트 삭제된 이미지 목록을 조회. 상위 블록 삭제 여부도 같이 응답(복구 버튼 비활성 목적).
* 예외: 권한 없음 → "프로젝트에 접근할 권한이 없습니다." / 프로젝트 없음 → "프로젝트를 찾을 수 없습니다."

**항목 생성**
* 무엇: 파일 1개 이상 업로드. 개별 20MB·1회 최대 15개·총 300MB. 5MB 초과 시 가로/세로 1920 기준 리사이즈(움짤 제외). jpg/jpeg/png/gif/webp만 허용(jpg/png/gif는 imageIO 2차 검증, webp는 매직바이트). 버킷이 비공개라 URL 유효기간 1시간. 생성 시 활동 로그.
* 예외: 형식 오류 → "지원하지 않는 파일 형식입니다." / 개수 불일치 → "이미지 개수와 캡션 개수가 일치하지 않습니다." / 개수 초과 → "한 번에 업로드할 수 있는 파일 개수를 초과했습니다." / 권한 없음 → "편집 권한이 없습니다." / 블록 없음 → "존재하지 않는 블록입니다."

**항목 수정**
* 무엇: 순서·캡션 변경, 삭제 처리. `version` 컬럼으로 동시 수정 방어. 전체 배열을 받는 방식이라 덮어쓰기는 지원하지 않고, 배열에서 빠진 항목은 삭제 처리. 삭제되면 재정렬하며 `version`도 같이 올림.
* 예외: 전체 배열 이상 → "요청한 이미지 목록이 유효하지 않습니다." / 버전 없음 → "버전 정보가 없습니다. 화면을 새로고침해 주세요." / 권한 없음 → "편집 권한이 없습니다." / 블록 없음 → "존재하지 않는 블록입니다." / 버전 충돌 → "다른 사용자가 먼저 수정했습니다."

**항목 삭제**
* 무엇: 이미지 항목 하나를 소프트 삭제. 삭제 후 재정렬하고 버전을 올린다. 활동 로그를 남긴다.
* 예외: 권한 없음 → "편집 권한이 없습니다." / 항목 없음 → "존재하지 않는 항목입니다."

**복구**
* 무엇: 휴지통에서 조회한 정보로 소프트 삭제된 이미지를 원래 블록으로 복구. 원래 순서가 아니라 맨 마지막 순서로 복구. 활동 로그를 남긴다.
* 예외: 배열 이상 → "요청한 이미지 목록이 유효하지 않습니다." / 권한 없음 → "편집 권한이 없습니다." / 항목 없음 → "존재하지 않는 항목입니다." / 상위 블록 삭제됨 → "상위 블록이 삭제되어 하위 항목을 복구할 수 없습니다."

**영구 삭제**
* 무엇: 휴지통에서 조회된 이미지들을 배열로 받아 영구 삭제(S3 삭제 + DB 하드 삭제).
* 예외: 배열 이상 → "요청한 이미지 목록이 유효하지 않습니다." / 권한 없음 → "편집 권한이 없습니다." / 항목 없음 → "존재하지 않는 항목입니다."

**프로젝트 이미지 모아보기**
* 무엇: 한 프로젝트의 모든 이미지를 조회. 블록·스텝 정보도 같이 내려줘 프론트가 "블록별 모아보기"도 구현할 수 있게 함.
* 예외: 권한 없음 → "프로젝트에 접근할 권한이 없습니다." / 프로젝트 없음 → "프로젝트를 찾을 수 없습니다."

### 정산 (5개)

**항목 수정 시 조회**
* 무엇: outcome 타입은 수정 시 원본 계좌번호를 보여주고, 신규 작성 시 같은 프로젝트에 이미 있는 총 금액·회차 번호를 추천.
* 예외: 타입 미지정 → "정산 블록의 타입 지정은 필수입니다." / 권한 없음 → "편집 권한이 없습니다." / 블록 없음 → "존재하지 않는 블록입니다." / 타입 변경(OUTCOME→INCOME) → "출금(OUTCOME)에서 입금(INCOME)으로는 타입을 변경할 수 없습니다."

**항목 작성/수정**
* 무엇: 최초 작성 시 타입(income/outcome) 선택, outcome은 은행정보 추가 입력. income→outcome 변경은 가능하나 역방향은 불가. 이미 연결된 블록이 있으면 총 금액을 다르게 지정 불가. 세금계산서·입출금 중 하나라도 연결돼 있으면 수정 불가. 수급 진행률·정산 상태·세금계산서 상태를 함께 보여줌. `version` 필수로 동시 수정 검증(덮어쓰기/재조회 선택). outcome 계좌번호는 암호화 저장, 조회 시 앞뒤 3자리만 남기고 마스킹.
* 예외: 타입 누락 → "정산 블록의 타입 지정은 필수입니다." / 내용 누락 → "내용을 입력해 주세요." / 출금 타입 계좌정보 누락 → "출금 타입은 계좌정보가 필수입니다." / 회차 번호 이상 → "회차 번호는 1 이상이어야 합니다." / 버전 없음 → "버전 정보가 없습니다. 화면을 새로고침해 주세요." / 권한 없음 → "편집 권한이 없습니다." / 블록 없음 → "존재하지 않는 블록입니다." / 타입 변경 → "출금(OUTCOME)에서 입금(INCOME)으로는 타입을 변경할 수 없습니다." / 재무 연결 상태 → "세금계산서 또는 입출금 내역이 연결되어 있어 수정할 수 없습니다." / 금액 불일치 → "같은 프로젝트의 다른 정산 블록과 총 예정 금액이 일치하지 않습니다." / 버전 충돌 → "다른 사용자가 먼저 수정했습니다."
* 모듈5에서의 메시지 암호화를 했던 경험으로 계좌번호 또한 DB가 유출되면 피해가 일어날 수 있는 정보라고 판단되어 암호화를 진행했습니다.

**필터 옵션 조회**
* 무엇: 한 회사에 연관된 발주처 정보를 조회 옵션으로 넘긴다.
* 예외: 권한 없음 → "접근 권한이 없습니다."

**프로젝트 조회**
* 무엇: 회사 단위 정산 현황을 프로젝트 단위로 조회. 세금계산서·입출금 미연결 개수, 지연일 정보 포함. 프론트 지정 형식대로 페이징.
* 예외: 페이징 오류 → "페이지 조회 조건이 올바르지 않습니다." / 권한 없음 → "접근 권한이 없습니다."

**블록 조회**
* 무엇: 프로젝트 내부 정산 블록 정보(연결 책임자, 세금계산서·입출금 연결 정보 등)를 조회.
* 예외: 권한 없음 → "접근 권한이 없습니다." / 상위 프로젝트 없음 → "존재하지 않는 프로젝트입니다."

## 🗄️ DBA 활동 — ERD·Flyway·스키마 설계 검토

기능 개발과 별개로, 팀 내 DBA 중 한 명으로서 스키마·마이그레이션 관련 의사결정에 참여했습니다.

* **ERD 정리**: 도메인이 늘어나며 흐트러진 ERD를 최신 상태로 정리했습니다.
* **Flyway 도입 리서치 및 공유**: Flyway 도입을 검토하는 단계에서 관련 자료를 조사해 다른 DBA와 공유했습니다.
* **초기 DDL 마이그레이션 순서 정리**: 초기 스키마의 테이블 간 FK 의존관계를 고려한 마이그레이션 순서를 배정현님과 함께 검토·정리했습니다.
* **템플릿 저장 방식 검토 — MongoDB vs MySQL+MyBatis**: 프로젝트 템플릿처럼 자유도가 높은 데이터를 다뤄야 하는 요구가 나왔을 때 NoSQL(MongoDB) 도입을 검토했습니다. 다만 (1) NoSQL에 대한 이해가 충분하지 않은 상태에서 도입하는 리스크, (2) MySQL과 MongoDB 두 개의 DB를 함께 개발·운영해야 하는 관리 부담을 고려해, **MySQL+MyBatis를 유지하고 자유도가 필요한 부분만 JSON 컬럼 타입으로 흡수하는 방향**을 제안했습니다.

> ⚠️ 이 DBA 활동들은 개별 도메인 코드가 아니라 팀 차원의 자료 조사·공유·논의로 이뤄진 것이라, 리포지토리 커밋 히스토리로는 직접 확인되지 않습니다.

### 5. 클라이언트 맞춤형 API 스펙 리팩토링

* **입출금/세금계산서 단건 조회 API 신설**: 프론트가 상세 화면 성능 최적화를 위해 요청. 목록 페이지네이션과 무관하게 ID 하나로 바로 조회하도록 `GET /api/v1/finance/cash-flows/{cashFlowId}`, `GET /api/v1/finance/tax-invoices/{taxId}`를 신설하고, 기존 목록 응답 타입을 그대로 재사용해 새 DTO 없이 구현.
* **입출금 응답에 `bankName` 추가**: 프론트가 은행명을 얻으려고 거래고유번호(`bankTxnId`)를 문자열로 잘라 되읽는 우회를 쓰고 있었는데, 그 접두어가 은행명 앞 4자만 써서 실제로 값이 깨지는 은행이 있었습니다. 이미 있는 `bank_name` 컬럼을 응답에 그대로 노출해 우회를 없앴습니다.
* **이미지 단건 삭제 시 재정렬 + 버전 동시 반영**: 이미지 하나를 삭제하면 뒤 순번 이미지들의 `orderIndex`를 당기도록 프론트 요청으로 구현했고, CodeRabbit 리뷰로 이 재정렬이 동시 수정 방어(`version`)도 함께 갖춰야 한다는 걸 반영해 보완했습니다.
* **정산 현황 계좌번호 마스킹 해제**: 정산 현황 블록 조회는 `FINANCE` 페이지 권한을 가진 재무팀만 도달하는 엔드포인트라는 걸 근거로, 실무 화면에서는 마스킹하던 계좌번호를 이 화면에서는 원본으로 노출하도록 변경 — 실제 송금 처리에 원본 값이 필요하다는 재무팀 요구를 반영.

## 5. 한계 및 향후 개선 과제 (Limitations & Next Steps)

* **직접 등록 입출금의 중복 검증 사각지대**: 직접 등록은 잔액을 입력받지 않아, 잔액을 제외한 나머지가 모두 같은 두 건은 중복으로 취급됩니다. 파일 업로드보다 수정 자유도를 우선한 의도된 트레이드오프로 남겨뒀습니다.
* **거래처 관계를 1:1로 가정한 설계**: 프로젝트 단위로 입금/출금 각각의 총 금액 동등성을 검증했는데, 실제로는 한 프로젝트에 같은 타입의 거래처가 여러 곳(N:M)일 수 있습니다. 다시 설계한다면 프로젝트 단위가 아니라 거래처명 단위로 총액을 추천·검증하는 방향을 검토하겠습니다.
* **`LIKE '%검색어%'` 구조적 한계**: 앞와일드카드 검색은 인덱스로 해결되지 않는 구조적 문제라, 현재는 검색 빈도가 낮을 것으로 판단해 우선순위를 낮췄습니다.
* **재무 도메인의 JPA 미사용**: 초기 개발 단계의 판단 미스로 재무 도메인이 MyBatis 위주로 굳어졌고, 이미 동시성 방어까지 그 구조 위에 쌓여 있어 구조 변경 없이 유지하기로 했습니다.
